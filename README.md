# مسار — حسابات حقيقية وبيانات سحابية مشتركة (Supabase)

تطبيق ثابت (HTML/CSS/JS بدون إطار عمل أو خطوة بناء) يعمل كسطح مكتب وتطبيق ويب قابل للتثبيت (PWA)، مع تخزين سحابي عبر مشروع Supabase مخصّص لمسار. البيانات مشتركة بين الحسابات المصرّح لها، والصلاحيات مطبّقة في قاعدة البيانات عبر RLS، وتصل الواجهة إلى Supabase مباشرة دون SDK خارجي.

**قبل أول تشغيل** لازم تنفّذ خطوات إعداد Supabase اليدوية أدناه (قسم "الإعداد السحابي") — بدونها التطبيق لن يعمل إطلاقًا (لا بيانات نائبة محلية بعد الآن).

## التشغيل محليًا

المتصفح يمنع `fetch`/الوحدات (`type="module"`) من العمل مباشرة عبر `file://`، فيجب تشغيله من خادم ثابت بسيط:

```bash
cd masar-app
python3 -m http.server 8080
# أو: npx serve .
```

ثم افتح `http://localhost:8080` في المتصفح.

### التثبيت على الآيفون (Add to Home Screen)

افتح رابط GitHub Pages في Safari، ثم اضغط زر المشاركة واختر **إضافة إلى الشاشة الرئيسية**. يعمل التطبيق بوضع مستقل مع أيقونة مخصّصة، ويعرض صفحة آمنة عند انقطاع الشبكة من دون تخزين بيانات الطلاب أو جلسة الدخول في كاش الـService Worker. على المتصفحات الداعمة يظهر زر تثبيت داخل التطبيق تلقائيًا.

### سجل الطلبة: استيراد من داخل التطبيق (وليس ملف بالمستودع)

بما إن هذا مستودع **عام** (لازم لاستضافة GitHub Pages المجانية)، ملف ثابت فيه بيانات طلاب حقيقية داخل المستودع كان
يعني أي زائر يقدر يجلبه مباشرة بدون تسجيل دخول — لذا سجل الطلبة يُستورد الآن **من داخل التطبيق نفسه**، خلف تسجيل
الدخول + RLS، تمامًا بنفس طريقة استيراد المرفعين:

من شاشة "سجل الطلبة" (فارغة أول مرة) أو زر "تحديث سجل الطلبة" (بعد أول استيراد) — ارفع ملف كشف الطلاب الكامل
نفسه (شيت "كشف الطلاب")، راجع عدد الصفوف بشاشة المعاينة، واعتمد. الاستيراد يستبدل السجل بالكامل كل مرة — كشف
الطلاب يُعاد إصداره كامل من إدارة المدرسة، مو دفعة تراكمية.
(`src/services/students-import-service.js` لمنطق التحويل، مفحوص صفًا بصف مقابل شكل البيانات الفعلي وشيت "كشف الطلاب"
الحقيقي.)

للتحديث الدوري الأسرع، الإدارة ← الاستيراد ← **تحديث شامل** يقرأ من الملف نفسه شيتات كشف الطلاب والمعلمين
والمرفعين، يعرض الأعداد والمطابقة، وينزّل نسخة احتياطية كاملة قبل الحفظ. مطابقة الأعمدة بالترويسة لا بموقع العمود،
وتُحفظ ملاحظات الطلاب وصور المعلمين، وتُدمج صفوف المرفعين المكررة بمفتاح الرقم الأكاديمي + المقرر.

**قالب المقررات محدَّث تلقائيًا من نفس الملف أيضًا — اختياري**: لو الملف يحتوي شيتي "الصناعي" و"التجاري" (نفس بنية
ملف "المقررات.xlsx": القسم، نوع المقرر، الفصل١..الفصل٦)، يُحدَّث قالب سجل المقررات بشاشة شهادة الطالب تلقائيًا وقت
التحديث الشامل — بدون حاجة لطلب تعديل الكود يدويًا كل مرة يصدر قالب مقررات جديد. الشيتان اختياريان تمامًا: غيابهما
لا يؤثر على تحديث الطلبة/المعلمين/المرفعين، ويبقى قالب المقررات المحفوظ كما هو. القالب نفسه مجموعة سحابية عادية
(`curriculumTemplates`، صف واحد لكل مسار) بدل ملف JS ثابت، فتُقرأ شاشة الشهادة قيمتها حيًّا بدل استيرادها وقت البناء.
خلايا القالب قد تحمل رمزين بديلين مفصولين بـ"/" (مثل `رسم803/رسم813`) لو اختلف رمز المقرر الفعلي بحسب فوج الطلبة
رغم تمثيله نفس بند المنهج — مطابقة درجة الطالب تجرّب كل رمز على حدة (`src/modules/grades/curriculum-results.js`).

بجانبه تبويب **تحديث الخطة**: يرفع ملف "الخطة التنفيذية" الرسمي (شيت واحد، صف عنوان ثم ترويسة ثم الإجراءات)
ويعرض عدد المشاريع/الإجراءات قبل الاعتماد. الاعتماد **استبدال كامل** لخطة القسم — كل مشاريعها وإجراءاتها الحالية
تُحذف وتُستبدل بمحتوى الملف، بما في ذلك أي محور غير موجود بالملف الجديد (يُنبَّه له صراحة بالمعاينة قبل التنفيذ).
تقدّم التنفيذ (`actionProgress`) وربط بنود تقرير المتابعة الرسمي للإجراءات القديمة يُحذفان معها تلقائيًا (عبر نفس
`deleteProject` المستخدمة بشاشة خطة القسم) لأنهما مرتبطان برقم الإجراء داخل مشروعه — خطة جديدة تبدأ بلا تنفيذ
مسجَّل ولا ربط، ويحتاجان إعادة تعبئة يدوية من الشاشة. مطابقة الأعمدة (بالاسم لا بموقع العمود): «المحور» و«البرنامج»
يحدّدان تجميع الإجراءات في مشاريع (كل مجموعة صفوف بنفس المحور والبرنامج = مشروع واحد)، «الفئة المستهدفة» → المستهدف
(مثل "طلاب المدرسة"، "طلبة المستوى الأول" — لا عمود "المستهدف" الرقمي/النسبي بالملف، غير مستخدَم)، «دور المكتب» →
المنفذ، «الأقسام المشاركة» → المتابع، «الثبوتيات» → الثبوتية، وتاريخا بدء/نهاية التنفيذ المقترحين (رقم تسلسلي إكسل)
يُحوَّلان لتاريخ حقيقي. أعمدة الملف الإضافية (بيانات الحصر المطلوبة، مؤشر الأداء KPI، عمود "المستهدف" الرقمي) غير
مخزَّنة حاليًا — بقرار صريح من المرشد لإبقاء نطاق التحديث بحقول الشاشة الحالية.
(`src/services/department-plan-import-service.js`.)

### تصدير تحديثات سجل الطلبة/المعلمين إلى Excel

التطبيق سحابي بالكامل ولا يكتب على أي ملف إكسل محلي مباشرة (لا وصول كتابة لملفات — File System Access API بالتطبيق
للقراءة فقط، راجع قسم "استيراد الدرجات والشهادات" أعلاه). لإبقاء نسخة المرشد المحلية (كشف الطلاب/المعلمين بجهازه أو
OneDrive) شبه محدَّثة بعد تعديلات تتم من داخل التطبيق (تعديل بيانات طالب/معلم، ملاحظات...)، تبويب **"تصدير
التحديثات"** بالاستيراد يولّد ملف Excel **بالتغييرات فقط منذ آخر تصدير** — لا كل السجل من الصفر كل مرة:

- عمود **"الحالة"** لكل صف: `جديد` (طالب/معلم لم يكن موجودًا وقت آخر تصدير)، `معدّل` (تغيّر حقل واحد على الأقل)،
  `محذوف` (كان موجودًا وقت آخر تصدير واختفى من السجل الحالي).
- **الأعمدة تقتصر على الحقول التي تغيّرت فعليًا** بأي صف ضمن هذا التصدير — لا الحقول كاملة (36 عمودًا) كل مرة؛ صف
  "معدّل" يعرض قيمته الحالية فقط بالحقول التي تغيّرت هو نفسه، وفارغ بالباقي (حتى لو ظهر عمودها لتغيّر بصف آخر).
  عمودا الهوية (الرقم الأكاديمي/الشخصي + الاسم) يظهران دائمًا بكل الصفوف لتحديد مين تغيّر.
- المقارنة مع آخر نسخة محفوظة **محليًا بمتصفح المستخدم فقط** (IndexedDB، `src/services/roster-export-snapshot.js`) —
  لا تُرسَل لـSupabase ولا تُشارَك بين الأجهزة. أول تصدير بلا نسخة سابقة: كل السجل الحالي يظهر كـ"جديد". بعد كل
  تصدير ناجح تُحدَّث النسخة المحفوظة تلقائيًا لتصير خط الأساس للمقارنة القادمة.
- **لماذا لا تلوين خلايا بدل عمود "الحالة"**: مكتبة SheetJS المجانية المُضمَّنة بالتطبيق (`src/vendor/xlsx.core.min.js`)
  لا تدعم كتابة تنسيق/تلوين الخلايا عند التصدير (ميزة حصرية بنسختها المدفوعة، تحقّقنا منها عمليًا) — عمود نصي قابل
  للفرز/الفلترة بـExcel مباشرة أعطى نفس الفائدة بلا حاجة لمكتبة إضافية.
- الحقول المقارَنة تطابق حقول نموذج التعديل بالضبط (لا حقول الجدول/الجدول الأسبوعي المستوردة فقط): للطلبة
  الاسم/الاسم الإنجليزي/الأرقام/البريد/المستوى/الشعبة/القسم/المسار/الهاتف/المواصلات/رقم المجمع/الملاحظات؛
  للمعلمين الاسم/الاسم الإنجليزي/الأرقام/المسمى الوظيفي/القسم/الهاتف/البريد/الملاحظات (الصور خارج النطاق، تُدار من
  شاشة المعلمين نفسها). صف واحد لكل طالب/معلم بلا تغيير حقيقي منذ آخر تصدير لا يظهر إطلاقًا — الملف بالكامل يبقى
  فارغًا (رسالة "لا توجد تحديثات") لو ما تغيّر شيء.
(`src/services/roster-changes-export-service.js` لمنطق المقارنة/بناء الصفوف، مُختبَر بالكامل بلا حاجة لمتصفح حقيقي.)

## ما يعمل فعليًا الآن (ببيانات حقيقية من ملفات القسم)

- **الرئيسية**: أُعيد تصميمها لتكون لوحة تنبيهات فعلية ("شنو يحتاجني اليوم؟") بدل تكرار أرقام ثابتة موجودة أصلًا بخطة القسم. أربع بطاقات مؤشرات كلها قابلة للتغيّر يوميًا: طلاب يحتاجون متابعة، حالات إرشادية مفتوحة بلا متابعة حديثة (14 يومًا فأكثر بدون جلسة أو فتح الحالة نفسها — `listStaleOpenCases` بـ`guidance-service.js`)، إجراءات خطط دعم متأخرة (تجاوزت `dueDate` ولم تُنجز، لخطة نشطة — `listOverdueActions` بـ`support-service.js`)، وعدد إجراءات الخطة اللي لم يبدأ تنفيذها بعد (`getAgendaProgressSummary` بـ`agenda-service.js` — بديل عن "إجراءات قريبة من نهاية فترتها" غير القابل للحساب فعليًا، لأن "فترة التنفيذ" بخطة القسم نص حر لا تواريخ حقيقية، مثال: "طوال العام الدراسي"). تحتها بطاقة "طلاب يحتاجون متابعة" التفصيلية (`src/modules/dashboard/followup-needs-service.js`، تجمع مرشحي الحالات/الدعم/التوجيه المهني بحسب الطالب)، وبطاقتا الحالات المتعثرة والإجراءات المتأخرة بالتفصيل، و**التذكيرات مدمجة بالكامل هنا** (عرض/إضافة/تبديل حالة/حذف) — لم تعد تبويبًا مستقلًا بالقائمة الجانبية. تبويبا "التحليل الأكاديمي" (الأضعف أكاديميًا وأكثر مقررات مرفّع معلّقة، أعلى 10 لكل قائمة) و"خطة القسم" (توزيع الإجراءات حسب المحور) **حيّان بالكامل** (2026-09-10) عبر `masar_dashboard_snapshot_v2` مباشرة — كانا سابقًا يظهران فقط بعد "تحديث من المجلد" (لقطة من نسخة احتياطية محلية بمجلد OneDrive)، وأُزيل ذلك الاعتماد نهائيًا لأنه كان يعرض بيانات قد تكون بعمر يوم أو أكثر دون تنبيه واضح. مجلد OneDrive المحلي لسا مستخدَم لصور الطلبة/المعلمين وجدول الطالب وشهادته فقط (`getMasarFolderHandle` بـ`dashboard-local-folder.js`)، بمعزل تام عن الرئيسية الآن.
- **خطة القسم**: 15 مشروعًا موزعة على 3 محاور (الانجاز الأكاديمي، التطور الشخصي، القيادة)، 153 إجراءً — من `الخطة الموحدة.xlsx` الفعلي (كانت 160، حُذفت 7 إجراءات تنظيمية داخلية بحتة بلا نظير في تقرير المتابعة الرسمي — انظر أدناه). **قابلة للتعديل بالكامل من داخل التطبيق**: إضافة/تعديل/حذف مشروع (المحور، العنوان، البرنامج، الهدف، رئيس الفريق)، وإضافة/تعديل/حذف إجراء داخل أي مشروع (النص، المستهدف، المنفذ، المتابع، الثبوتية، فترة التنفيذ، **وربطه ببند تقرير المتابعة الرسمي** — انظر أدناه). حذف مشروع أو إجراء يحذف معه أي تقدّم تنفيذ (`actionProgress`) مرتبط به تلقائيًا، فلا تبقى سجلات يتيمة تشير لإجراء لم يعد موجودًا — رقم الإجراء (`no`) لا يُعاد استخدامه أبدًا بعد حذفه، لأن حالة التنفيذ وربط تقرير المتابعة يعتمدان عليه كمعرّف ثابت. **بحث سريع عن إجراء** (بنص الإجراء/المستهدف/المنفذ/المتابع) أعلى الشاشة يبحث عبر كل المحاور معًا، والضغط على نتيجة يبدّل المحور تلقائيًا ويفتح نموذج تعديل الإجراء مباشرة — بدل تصفح يدوي بين المحاور والمشاريع.
- **الأجندة التنفيذية**: تبويبان لطريقة تنظيم الإجراءات، بطلب المرشد بعد ملاحظة إن التجميع بالنص وحده كان يخلط إجراءات متفاوتة زمنيًا بمجموعة واحدة ("طوال العام الدراسي" مثلًا تجمع كل الإجراءات مهما كان تاريخها الفعلي):
  - **"حسب التاريخ" (الافتراضي)**: تجميع بحسب الشهر الفعلي من **تاريخ بداية التنفيذ الرقمي** (`periodStart` — اختياري، من نموذج تعديل الإجراء بخطة القسم)، بغض النظر عن نص الفترة الأصلي. الأشهر مرتَّبة زمنيًا تصاعديًا (`groupByMonth` بـ`agenda-service.js`)، وأي إجراء بلا تاريخ محدد يظهر بمجموعة "بلا تاريخ محدد" الوحيدة دائمًا بآخر القائمة.
  - **"حسب نص الفترة"**: التجميع القديم — بحسب النص الأصلي من الملف كما هو ("الأسبوع الثاني من سبتمبر"، "طوال العام الدراسي"، "فترة الامتحانات النهائية"...)، بلا تعديل على النص نفسه ولا على شرط "لازم وصف فترة نصي حتى لو حُدِّد تاريخ" (`groupByPeriod`).
  - **داخل أي مجموعة بكلا الوضعين**: الإجراءات مرتَّبة زمنيًا بحسب تاريخ بدايتها (فنهايتها عند تساوي البداية) — بدل ترتيب ظهورها العشوائي بالملف الأصلي؛ إجراء بلا تاريخ يُدفع لآخر مجموعته، لا يختلط عشوائيًا بين الإجراءات المؤرَّخة.
- **إنجاز الخطة الفعلي**: نسبة الإجراءات المكتملة من الـ153 إجراءً، محسوبة **حيًّا** من `actionProgress` (نفس حالة كل إجراء المسجَّلة من شاشة الأجندة التنفيذية أو من نموذج تعديل الإجراء بخطة القسم) — بدل لقطة تقرير المتابعة الرسمي القديمة التي كانت أحيانًا تتناقض مع حالة نفس الإجراء. بطاقتا "إنجاز الخطة الفعلي" و"إجراءات متبقية" بشاشة خطة القسم قابلتان للضغط لعرض قائمة الإجراءات نفسها، والضغط على أي إجراء يوديك لتعديله مباشرة. سجلات `agendaStatus` التاريخية الـ55 نُسخت احتياطيًا ثم نُظفت من الإنتاج في 2026-09-06.
- **التذكيرات**: قائمة تُدار يدويًا بالكامل (إضافة/تبديل الحالة/حذف)، لا اشتقاق تلقائي من الأجندة بعد. **مدمجة بالكامل بالرئيسية الآن** (`src/modules/reminders/reminders-service.js` لا يزال هو منطق البيانات، لكن لا شاشة/تبويب مستقل له بعد الآن).
- **سجل الطلبة**: 1398 طالبًا فعليًا من كشف الطلاب — لوحة أعداد المستويات والمسارين، بحث وتصفية حسب المستوى/القسم/المسار/الشعبة، وطباعة كشف شعبة قابل لتخصيص العنوان والتعليمات. ملف كل طالب يعرض التواصل ومرشد الشعبة وجدول الشعبة داخل الصفحة والمسار الأكاديمي. البيانات مشتركة سحابيًا لكل الحسابات النشطة، والقائمة مُقسَّمة صفحات (50 لكل دفعة).
  - **صور الطلبة محلية وخفيفة**: لا تُرفع إلى Supabase ولا تدخل النسخ الاحتياطية. يقرأ التطبيق صور JPG/PNG/WebP/GIF من مجلد مسار المرتبط في OneDrive ويطابق اسم الملف بالرقم الأكاديمي (أو الرقم الشخصي عند الحاجة)، ثم يعرضها داخل المتصفح فقط.
- **تقرير المتابعة الرسمي مدموج داخل خطة القسم** (لا شاشة مستقلة بعد الآن): بطلب صريح من المرشد لتقليل التنقل بين الشاشات لنفس البيانات. من نموذج تعديل أي إجراء بخطة القسم، حقل "بند تقرير المتابعة الرسمي" يربطه بواحد من الـ26 بندًا الرسمية (المنطقة التعليمية). زرّا عرض أعلى خطة القسم: "حسب المحور" (الوضع الافتراضي) و"حسب بند تقرير المتابعة" — الثاني يبدّل العرض من تقسيم حسب المحاور الثلاثة إلى تقسيم حسب الـ26 بندًا الرسمية، كل بند يعرض حالته المحسوبة تلقائيًا (من حالة الإجراءات المرتبطة به: الكل "تم" ⇒ تم) وقائمة الإجراءات المرتبطة، قابلة للضغط للقفز مباشرة لتعديل أي إجراء منها. قسم "إجراءات غير مربوطة بأي بند" بنفس العرض يكشف أي إجراء لسا ما اتحدد له بند رسمي. زر "تصدير تقرير المتابعة (Word)" بأعلى الشاشة يولّد نفس صيغة التقرير الرسمي وقت الحاجة للتسليم، دون شاشة تصفح يومية منفصلة.
  - **بلا إدخال يدوي منفصل بعد الآن**: بند بلا أي إجراء مرتبط يظهر "لم يبدأ" — يكشف فجوة حقيقية (بند رسمي ما له نظير بالخطة بعد) بدل تغطيتها برقم مُدخَل يدويًا منفصل عن الإجراءات الفعلية. **خطة القسم صارت المصدر الوحيد لكل الإحصائيات** بلا استثناء، بقرار صريح من المرشد.
  - **ربط كامل** (`src/services/action-followup-links.js`): بعد مراجعة المرشد للربط الأولي (كان 131 من أصل 160)، **كل الإجراءات الـ153 الباقية مربوطة الآن ببند التقرير المناسب**، بلا استثناء. الـ7 إجراءات اللي ما قابلها أي بند رسمي بثقة كافية — نشاطات تنظيمية داخل القسم بحتة (تشكيل فريق مرشد الشعبة، إنشاء مجموعة تيمز، تكريم المعلمين، معلم الظل، أدوار قيادية للطلاب بالحياة المدرسية، فتح قنوات تواصل متعددة، نشر ثقافة المحافظة على البيئة المدرسية) — **حُذفت من خطة القسم نهائيًا** بعد مراجعة المرشد وتأكيده، بدل أن تبقى بلا ربط. ملاحظة مهمة اكتُشفت أثناء المراجعة: "الساعة الذهبية" كانت مصنَّفة كبرنامج داخلي بلا نظير، لكن ملخص البند الرسمي ٢٤ ("المشاريع الإبداعية المتميزة لمكتب الإرشاد") يوثّقها فعليًا حرفيًا — فرُبطت به. **الربط اجتهاد يحتاج مراجعة دورية** من نموذج تعديل الإجراء بخطة القسم.
- **الدرجات والتحليلات: استيراد الشهادات (PDF) صار من شاشة الاستيراد** — راجع قسم "استيراد الدرجات والشهادات: من داخل التطبيق مباشرة" أدناه للتصميم الكامل. شاشة "الدرجات والتحليلات" نفسها تعرض تبويبَي التحليلات وتصنيف الطلاب فقط، من مجموعة `academicFlags` (بيانات مجمَّعة جاهزة، لا صفوف درجات خام) و`termAverages` (معدلات فصلية رسمية).
  - **تصنيف الطلاب** (تبويب ثانٍ): كل طالب له صف بـ`academicFlags` يُصنَّف تلقائيًا إلى متفوقين (٩٠٪ فأكثر)/متوسطي التحصيل (٦٠-٩٠٪)/متدني التحصيل (أقل من ٦٠٪) — حدود عمل المرشد نفسه (`achievement-service.js`)، منفصلة عن سلّم تقدير الوزارة الرسمي (راسب/مقبول/متوسط/جيد/جيد جدًا/ممتاز) الذي يبقى ظاهرًا كتقدير لكل طالب بجانب تصنيفه. بطاقة "يحتاجون تدخل (دعم أكاديمي)" بنفس الشاشة تستخدم بالضبط نفس قائمة مرشحي خطط الدعم/الحالات الإرشادية (`grade-flags-service.js`)، فلا تختلف الأرقام بين الشاشات.
    تصنيفان مستقلان داخل نفس التبويب: **"حسب المعدل العام"** (معدل الطالب الكلي عبر كل موادّه)، و**"حسب المادة"** (لكل مقرر على حدة — طالب متفوق عمومًا قد يكون متدني التحصيل في مادة واحدة تحديدًا، وهذا لا يظهر إلا في العرض المستقل لكل مادة).
- **المسار الأكاديمي لكل طالب** (داخل ملف الطالب في سجل الطلبة): منحنى للمعدل الفصلي عبر الزمن فقط — من `termAverages` الرسمي (المطبوع على شهادة الطالب)، لا يدخل فيه أبدًا درجات الوقفة التقويمية. الجدول المحوري لكل مقرر عبر الفصول (كان هنا سابقًا) أُزيل بإزالة تخزين صفوف الدرجات نفسها من مسار — راجع القسم أدناه.

- **النسخ الاحتياطي**: الإدمن فقط يصدّر كل بيانات مسار إلى ملف JSON واحد عبر RPC واحد، ويستعيد نسخة مع شاشة تأكيد قبل الاستبدال.
- **تسجيل دخول حقيقي (Supabase Auth)**: شاشة اسم مستخدم/إيميل + كلمة مرور (`src/services/auth-service.js`) تظهر دون جلسة صالحة، ولا يوجد تسجيل عام. يدير الإدمن الحسابات وثلاثة أدوار: `admin` للإدارة الكاملة، `counselor` لبيانات المتابعة اليومية، و`read_only` للعرض فقط. تفرض RLS هذه الحدود حتى عند إرسال طلب مباشر خارج الواجهة، وتُسجَّل العمليات الحساسة في `audit_logs` ببيانات وصفية دون نسخ المحتوى الطلابي.
  - **شاشة دخول معزولة وصولية بالكامل**: `#app-shell` مخفي حتى نجاح الدخول، والحقول ورسائل الخطأ مربوطة وصوليًا. يمكن إظهار/إخفاء كلمة المرور وطلب رابط استرجاعها؛ رد طلب الاسترجاع عام ولا يكشف إن كان الحساب موجودًا، وتوجد شاشة آمنة لتعيين كلمة مرور جديدة من رابط Supabase.
  - **انتهاء الجلسة يُعالَج مركزيًا**: أي 401 من أي طلب REST (نقطة عبور واحدة بـ`cloud-runtime.js`) يمسح الجلسة ويُعيد تحميل الصفحة تلقائيًا، فتظهر شاشة الدخول برسالة "انتهت جلستك" بدل خطأ REST خام. فشل الشبكة (انقطاع اتصال) يظهر برسالة عربية مفهومة بدل خطأ متصفح تقني، من نفس نقطة العبور — يغطي كل الشاشات، مو تسجيل الدخول فقط.
  - **الصفحة الحالية تنجو من تحديث المتصفح (F5)** عبر `location.hash` (بدون نظام توجيه كامل جديد)، والتركيز يرجع تلقائيًا لأعلى المحتوى الرئيسي بعد كل تنقّل بين الشاشات.
- **القائمة الجانبية مُعاد تنظيمها منطقيًا** بثلاث مجموعات. قسم الإدارة (الاستيراد، النسخ الاحتياطي، إدارة المستخدمين) للإدمن فقط، ويُحجب في الواجهة وتمنع عملياته RLS. على الهاتف تتحول القائمة إلى درج جانبي ملائم للمس، ويأخذ التطبيق مساحات الأمان الخاصة بشاشة الآيفون عند تشغيله من الشاشة الرئيسية.
- **مراجعة استجابة وصولية شاملة** (5 مقاسات: 320×568 حتى 1280×800، فحص axe-core آليًا على كل الشاشات المُسجَّل دخولها + شاشة الدخول): لا تمرير أفقي على أي مقاس، أزرار وحقول الإدخال بارتفاع ≥44px على الهاتف (`@media (max-width:860px)`)، تصحيح تباين نص ذهبي/أزرق فاتح لم يكن يحقق 4.5:1 فعليًا (`--on-gold` متغيّر ثابت عبر الوضعين الفاتح/الداكن لزر `.btn-primary` والعنصر النشط بالقائمة، وتغميق `--ink-500` بالوضع الفاتح من 3.8:1 إلى 4.93:1)، تصحيح ترتيب العناوين (كل عناوين البطاقات كانت `h3` مباشرة تحت `h1` بلا `h2` — 47 موضعًا بـ12 ملفًا)، وربط 29 حقل إدخال إضافي بتسمياته (`for`/`id` أو `aria-label` لحقول الرفع/القوائم بلا تسمية مرئية). النتيجة: صفر مخالفات axe عبر كل الشاشات المفحوصة، صفر انحدار بـ146 اختبار npm ونصوص Playwright السابقة (الدخول/القائمة/الاستجابة).
- **حالات واجهة مشتركة** (`src/modules/shared/ui-states.js`): تحميل/فراغ/خطأ (`loadingHtml`/`emptyHtml`/`errorHtml`، كل منها بـ`role`/`aria-live` مناسب) بدل تكرار نفس نص "جارٍ التحميل…" بكل شاشة، إشعار عابر مُعلَن لقارئ الشاشة (`showToast`) بدل `alert()` الحاجب — لا يوجد استدعاء `alert()` متبقٍ بأي شاشة بعد الآن؛ بعض الشاشات تعرض رسائل الخطأ/النجاح مضمَّنة داخل الصفحة نفسها (`<p class="hint">`) بدل إشعار عابر، وهي نمط ثانٍ مقبول لا `alert()` حاجب. كذلك تحقّق نوع (`.json`) وحجم الملف قبل قراءة أي استيراد نسخة احتياطية.
- **المتابعات والحالات الإرشادية**: حالة تُفتح لطالب معيّن (فئة أكاديمية/سلوكية/اجتماعية/نفسية + عنوان وملاحظات)، مع جلسات متابعة متعددة عبر الوقت (تاريخ، ملاحظة، الخطوة التالية) وحالة (مفتوحة/مُغلقة). **مرشَّحة تلقائيًا من الدرجات المستوردة**: أي طالب معدله العام أو إحدى مواده أقل من 50٪ (`src/modules/grades/grade-flags-service.js`) يظهر في لوحة "مرشحون من الدرجات" أعلى الشاشة، ما لم يكن لديه حالة مفتوحة أصلًا — زر واحد يفتح له حالة بالسبب مكتوبًا مسبقًا. لا حاجة لإدخال بيانات الطالب يدويًا؛ اختيار الطالب لحالة جديدة يدويًا عبر بحث مباشر بالاسم أو الرقم الأكاديمي (`src/modules/shared/student-picker.js`).

  - الحد الأدنى للترشيح (50٪) رقم واحد مركزي في `grade-flags-service.js` — تغييره مستقبلًا (إن اختلف سلّم النجاح الفعلي للمدرسة) يُحدَّث في مكان واحد فقط لكلا الشاشتين.
- **الطلاب المرفعين**: استيراد فعلي لشيت "المرفعين" من داخل ملف كشف الطلاب الكامل (نفس الملف متعدد الشيتات، يُكتشف الشيت المطلوب تلقائيًا بالاسم) — كل صف مقرر لم يُستوفَ من الإعدادية لكل طالب، بحالة (اجتاز/لم يجتز بعد)، بنفس نمط المراجعة/الاعتماد/التراجع المستخدم بشاشات الاستيراد الأخرى. شاشة "طلاب لديهم مقررات لم تُجتَز بعد" تجمعهم بحسب الطالب، وتنبيه في ملف الطالب نفسه، وشارة رابعة في بطاقة "طلاب يحتاجون متابعة" بالرئيسية. اختُبر فعليًا على الملف الكامل (822 صفًا، 811 مطابقًا، 448 طالبًا لديهم مقرر معلَّق). هذه الشاشة تعرض قائمة الطلاب المعلَّقين فقط الآن — الاستيراد صار من الإدارة ← الاستيراد (إدمن فقط).
  - **الجدول الدراسي التفصيلي والساعات المكتبية: أُزيلا بالكامل** (قرار "Less App, More Intelligence" — بيانات مرجعية مؤسسية لا علاقة إرشادية مباشرة لها، خارج ما يحتاجه المرشد يوميًا). حُذف `src/modules/schedule/` (`schedule-service.js`) و`src/services/schedule-pdf-parser.js` بالكامل، وأزيلت بطاقتا استيراد "الجدول الدراسي والساعات المكتبية" و"استيراد جدول شعب (PDF)" من شاشة الطلاب المرفعين، وعرض الجدول الأسبوعي/الساعات المكتبية من ملف الطالب. مجموعتا `teacherSchedule`/`officeHours` أُزيلتا من قائمة المجموعات المدعومة (`src/core/config.js`)، والجدولان الفعليان بقاعدة البيانات نفسها محذوفان أيضًا الآن عبر `20260827_grades_import_to_cowork.sql` (نفس الملف اللي ينقل استيراد الدرجات لـCowork — راجع القسم المخصص أدناه).
- **التوجيه المهني**: سجل جلسات توجيه جامعي/مهني لكل طالب (موضوع، ملاحظات، وتوصية نهائية اختيارية)، معروض كقائمة طلاب (كل من لديه جلسة واحدة على الأقل) بدل سجل جلسات مسطَّح، لأن وحدة المتابعة هنا هي تاريخ الطالب لا الجلسة المفردة. **مرشَّحة تلقائيًا**: طلاب المستوى الثالث (السنة النهائية في هذه المدرسة) الذين لم تُسجَّل لهم أي جلسة بعد يظهرون في لوحة "طلاب السنة النهائية بلا جلسة توجيه" — هذا الترشيح مبني على مستوى الطالب من سجل الطلبة، بخلاف ترشيح الحالات/الدعم المبني على الدرجات.
- **تصدير التقارير كـ Word**: زر "تصدير Word" في خمس شاشات — خطة القسم (تقرير المتابعة الرسمي)، الأجندة التنفيذية (تقرير الإجراءات)، المتابعات والحالات الإرشادية، خطط الدعم الفردية، وملف كل طالب (زر "تصدير ملف الطالب" بأعلى صفحته). يُنتج ملف `.doc` حقيقي عبر تقنية Office HTML القياسية (محتوى HTML منسَّق بترويسة `xmlns:w` ونوع MIME `application/msword`) — بلا مكتبة خارجية مُضمَّنة، يفتح في Word مباشرة. البيانات نفسها المعروضة في الشاشة، منسَّقة كجداول جاهزة للطباعة أو التسليم. (`src/services/report-builders.js` لبناء محتوى كل تقرير، `src/services/word-export.js` للتنزيل).

## استيراد الدرجات والشهادات: من داخل التطبيق مباشرة

الاستيراد السابق (إكسل — كشوف درجات الوقفة التقويمية، وشهادات PDF لكل طالب عبر `certificate-parser.js`) انتقل بالكامل خارج مسار لفترة (سكربت Node منفصل اسمه Cowork)، ثم رجع لداخل التطبيق (2026-09-11) بعد ما تبيّن إن سكربت خارجي منفصل — يحتاج Node.js/Terminal على جهاز المرشد ومصدر بيانات منفصل — يشتّت أكثر مما يفيد، بينما إمكانية القراءة المحلية (File System Access API) موجودة بالتطبيق أصلًا لأغراض ثانية (صور الطلبة والمعلمين وجداول/شهادات الطلبة). القرار الحالي والعقد الدقيق:

**مصدر واحد فقط — شهادات PDF الرسمية**: `academicFlags`/`termAverages` تُحسَب من شهادات "سجل الطالب الدراسي" الرسمية فقط، بلا استثناء — لا دمج مع أي كشف درجات وقفة تقويمية أو مصدر جزئي غير رسمي (قرار صريح من المرشد: التقييم الجزئي غير الرسمي لا يجوز خلطه بمعدل مبني على شهادة معتمدة).

**لماذا صف مجمَّع لا صف درجة خام**: مسار كان يخزّن صف درجة واحد لكل طالب × مقرر × فصل (22,982+ صفًا فعليًا) فقط ليحسب منه لاحقًا معدلات ومرشَّحين — تخزين خام لداعي حسابي بحت لا لزوم له. بدله: صف واحد مجمَّع جاهز لكل طالب بـ`academicFlags`.

**العقد**: مجموعة `academicFlags`، **صف واحد لكل طالب** (لا لكل مقرر ولا لكل فصل):

```json
{
  "id": "<studentId>",
```

اسم المقرر موحّد (لا رمز) — عبر نفس جدول "المقررات" الرسمي (`src/services/subject-groups-seed.js`، بيانات مرجعية مؤسسية لا طلابية) ونفس اصطلاح المدرسة أن الدرجة **"0.5"** الحرفية تعني غيابًا لا 0.5٪. `termAverages` (معدل فصلي رسمي لكل طالب × فصل، من الشهادة) رقم مجمَّع مستقل، لا صف خام. ويُستخرج الحقل `finalCumulativeAverage` بصورة مستقلة من سطر **«المعدل التراكمي النهائي»** أسفل الشهادة؛ لا يُستبدل أبدًا بـ`overallPct` المحسوب من صفوف المقررات.

**طريقة التحديث**: الإدارة ← الاستيراد ← تبويب **"تحديث المعدلات"** — يمسح المتصفح نفسه مجلد "مسار" المحلي (نفس مجلد صور الطلبة والمعلمين وجداول/شهادات الطلبة، وصول File System Access API، كروم/إيدج فقط) بحثًا عن شهادات PDF، يحلّلها بـpdf.js المُضمَّن أصلًا بالتطبيق، ويكتب النتيجة مباشرة لـSupabase — بلا حاجة لجهاز منفصل ولا Node.js ولا تسجيل دخول ثانٍ (المستخدم مسجَّل دخوله بالتطبيق أصلًا، بنفس صلاحياته عبر RLS). **استبدال كامل لا تراكم**: كل تشغيلة تكتب `academicFlags`/`termAverages` من الصفر من كل الشهادات الموجودة بالمجلد وقت المسح، وتحذف تلقائيًا كل طالب لم تعد له شهادة بهذا المسح — شغّله دائمًا على مجلد الشهادات الكامل، لا فقط الملفات الجديدة. صف `termAverages` مكرَّر لنفس الطالب/الفترة (شهادة موجودة مرتين) يُدمَج بصف واحد (آخر ملف يُقرأ يُعتمَد) مع تنبيه بالمعاينة لو القيم متعارضة. الجدول أدناه يعرض عدد الشهادات المقروءة، الطلاب المطابقين، جداول الحصص المتجاهَلة، والملفات المشكوك فيها — قبل أي كتابة فعلية.

طبقة `src/services/academic-averages-import-service.js` (منطق المطابقة/التجميع، قابل للاختبار بلا متصفح حقيقي) تستدعي وحدات `scripts/lib/certificate-parser.mjs`، `document-classifier.mjs`، `subject-groups.mjs`، `score-conventions.mjs` مباشرة من المتصفح (نفس النمط المستخدَم أصلًا بشاشة شهادة الطالب الفردية، `student-certificate-local.js`) — بلا نسخ ولا اختلاف بالمنطق. استخراج نص PDF نفسه مشترك بـ`src/services/pdf-text-rows.js`. هذه الوحدات الأربع بـ`scripts/lib/` جزء أساسي من التطبيق الآن (لا سكربت منفصل يستهلكها)، مُختبَرة بـ`tests/scripts-*.test.mjs`.

**حماية من ملفات غير شهادات**: أرشيف "الشهادات" الحقيقي قد يختلط بملفات **"جدول حصص الفصل الدراسي"** (نفس نوع ملف جدول الشعب الرسمي، لا علاقة له بالدرجات، لكنه مليء برموز مقررات متكررة قد تُلتقَط بالغلط كمقررات طالب لو صادف رقمًا شبه رقم أكاديمي). `document-classifier.mjs` يتعرّف على جدول الحصص من شكله (عبارة "جدول حصص" أو تركيبة "الشعبة"/"مقرر"/"مدرس"/"غرفة") ويتجاهله صراحةً، بالإضافة لسقف منطقي لعدد المقررات بالفصل الواحد (`MAX_PLAUSIBLE_SUBJECTS_PER_TERM = 25`) يرفض أي ملف يتجاوزه كمؤشر تطابق بالصدفة.

**مسار يبقى صاحب القرار الوحيد** بحد الترشيح (50٪ — لا يزال رقمًا واحدًا مركزيًا بـ`grade-flags-service.js`) وسلّم التصنيف (متفوق/متوسط/متدني بـ`achievement-service.js`) — يقرأ فقط النسب المئوية الجاهزة من `academicFlags` ويطبّق عليها نفس المنطق القديم بالضبط؛ لا يعيد حساب أي شيء من صف خام لأنه لا يرى صفوفًا خامًا إطلاقًا.

**ما تغيّر فعليًا بالواجهة**:
- لا تبويب استيراد منفصل للدرجات/الشهادات بشاشة "الدرجات والتحليلات" نفسها (تعرض التحليلات والتصنيف فقط) — تحديث المعدلات صار بشاشة الإدارة ← الاستيراد مثل بقية التحديثات.
- المسار الأكاديمي بملف الطالب صار منحنى المعدل الفصلي فقط؛ الجدول المحوري (مقرر × فصل) أُزيل لأنه كان يعتمد على صفوف الدرجات الخام تحديدًا.
- الجداول المحذوفة من قاعدة بيانات مسار (migration `20260827_grades_import_to_cowork.sql`): `grades`، `importBatches`. دالتا Postgres `masar_grade_summaries`/`masar_dashboard_snapshot` أُلغيتا معهما — الرئيسية رجعت لتركيب لقطتها بجافاسكربت مباشرة، لأن `academicFlags` صار صغيرًا كفاية (صف لكل طالب) أن يفقد التحسين مبرره الأصلي.

## الإعداد السحابي (Supabase) — خطوات لازم تُنفَّذ يدويًا مرة واحدة

الكود جاهز بالكامل بالمستودع، لكن إنشاء الحساب/المشروع السحابي نفسه يحتاج صلاحيات لا تتوفر من جلسة العمل هذه — الخطوات التالية على محمد:

1. **إنشاء مشروع Supabase جديد** على [supabase.com](https://supabase.com) — اسم مقترح `masar-app`. **منفصل تمامًا عن مشروع CCE** (لا يُستخدم نفس المشروع إطلاقًا — بيانات طلاب مدرسة حقيقية لا تُخلط ببيانات نادي فرسان).
2. من Project Settings → **API Keys** (أو **Data API** حسب نسخة اللوحة): انسخ **Project URL**، و**anon public key** (بلوحات Supabase الأحدث اسمه **Publishable key**، يبدأ بـ `sb_publishable_...` — نفس الدور بالضبط). ضعهما في `src/services/supabase-config.js` مكان القيم النائبة (`SB_URL`/`SB_KEY`). آمن حفظهما بالكود مباشرة — نفس CCE بالضبط — الحماية الفعلية للبيانات عبر تسجيل الدخول + RLS، وليس بإخفاء هذا المفتاح.
   - من Authentication → URL Configuration أضف رابط GitHub Pages `https://mhshaban.github.io/masar-app/` إلى Redirect URLs حتى تعمل روابط استعادة كلمة المرور بعد النشر.
3. **تشغيل ملفات SQL بالترتيب الزمني**: افتح SQL Editor ونفّذ ملفات `supabase/migrations/` بحسب الاسم. رفع الملفات إلى GitHub لا يطبّقها تلقائيًا. تخزين صور الطلبة السحابي القديم يُلغى بـ`20260827_remove_student_photos.sql`؛ ميزة الصور الحالية لا تحتاج migration لأنها تقرأ الملفات محليًا من OneDrive.
4. **نشر Edge Function**: من تبويب Edge Functions بلوحة التحكم، أنشئ دالة باسم `admin-users` والصق محتوى `supabase/functions/admin-users/index.ts`، ثم Deploy. **لا حاجة لإضافة أي Secret يدويًا** — Supabase توفر `SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` تلقائيًا كـ"Default secrets" جاهزة بكل مشروع (تظهر تحت Edge Functions → Secrets → "Default secrets"؛ الأسماء القديمة عليها علامة Deprecated لكنها لسا شغالة، والكود يتعامل مع الصيغة الأحدث JSON أيضًا احتياطًا).
5. **Bootstrap أول حساب إدمن** (المشكلة الوحيدة الدائرية: إنشاء الحسابات يحتاج حساب إدمن موجود مسبقًا):
   - من تبويب Authentication بلوحة التحكم، أنشئ مستخدمًا واحدًا يدويًا (بريد إلكتروني حقيقي أو داخلي، وكلمة مرور).
   - من SQL Editor، نفّذ سطرًا واحدًا لترقيته لإدمن (استبدل البريد بالبريد اللي استخدمته):
     ```sql
     update public.profiles set role = 'admin', is_admin = true where email = 'your-email@example.com';
     ```
   - سجّل دخولك بالتطبيق بهذا الحساب — تقدر الآن تنشئ بقية حسابات المرشدين من شاشة "إدارة المستخدمين" مباشرة.
6. **ترحيل البيانات المحلية القديمة** (إن وُجدت من نسخة سابقة محلية على جهازك): من نسخة التطبيق القديمة صدّر نسخة احتياطية JSON (شاشة "النسخ الاحتياطي")، ثم سجّل دخولك بالنسخة السحابية الجديدة واستوردها من نفس الشاشة.
7. **الاستضافة**: بعد التأكد كل شي شغال، استضافة التطبيق (GitHub Pages مثلًا) تصير خيارًا آمنًا حتى لو كان الرابط عامًا — لأن البيانات الحقيقية محمية بتسجيل الدخول + RLS بقاعدة البيانات، مو بإخفاء الرابط.
